# 寄り道ランドマーク探索機能 要件定義書

## 1. 文書の目的

本書は、目的地へ向かう散歩中に、周辺のランドマークを「寄り道スポット」として発見する機能の要件を定義する。

本書は [`value-proposition.md`](./value-proposition.md) を前提とし、既存の [`requirements_MVP.md`](./requirements_MVP.md) に対する追加機能を扱う。既存の目的地設定、位置情報取得、目的地への距離・方角案内、散歩の開始・終了は変更しない。

実装時に判断が分かれないよう、以下を区別して記載する。

- **確定要件**: 初期実装で満たす要件
- **拡張要件**: 初期実装の対象外だが、追加可能な構造にする要件
- **未決事項**: ユーザー検証または共同開発者との合意後に決定する事項

未決事項を実装者の判断だけで確定してはならない。初期実装に値が必要な場合は、定数や設定として一か所に集約し、後から変更できるようにする。

---

## 2. 背景と提供価値

東京には、地域に根付いた店舗、歴史的建築物、文化、暮らしの痕跡などが存在する。一方、流行の店舗や新しい建物が目立つことで、それらを歩行者が偶然見つけることは難しい。

本機能はランドマークの詳細や正確な経路を最初から提示せず、「近くに何かある」という気配と方角だけを手掛かりとして提供する。利用者自身が周囲を見渡し、自分の足で近づき、自分のタイミングで情報を開く体験を重視する。

ランドマークには東京都が公開するオープンデータを利用する。元データはバックエンド側へ取り込み、アプリ用の共通形式に正規化して提供する。フロントエンドが東京都の配布元へ直接アクセスする構成にはしない。

### 中心となる体験

> 目的地へ向かう安心感を維持しながら、街に隠れた魅力の気配に気づき、自分で寄り道して発見する。

### 設計原則

1. **目的地を失わせない**: 寄り道中も、本来の目的地と散歩セッションを保持する。
2. **答えを先に見せない**: 発見前は名称や詳細を表示せず、存在の気配を示す。
3. **利用者が発見を確定する**: 自動的に詳細画面を開かず、利用者が「？」を押して情報を開く。
4. **正誤判定をしない**: ランドマークを当てるクイズにはしない。
5. **経路を指示しない**: 寄り道スポットへのルートや曲がり角を表示せず、初期実装では方角だけを示す。
6. **段階的に拡張できる**: 距離、接近状態、通知方法、詳細情報、振り返り機能を後から追加できる構造にする。

## 3. 対象利用者と利用場面

### 3.1 対象利用者

- 東京を日常的に歩く一般利用者
- 東京を観光で訪れる一般利用者
- 目的地へ向かう途中にも、その地域固有の店、建物、歴史または文化を発見したい人

学校教育での利用は現時点では対象外とし、将来検討とする。

### 3.2 初期実装の利用場面

1. 利用者が目的地を設定する。
2. 利用者が散歩を開始する。
3. アプリは目的地への方角を表示する。
4. 散歩中、周辺に発見可能な寄り道スポットが存在する。
5. 利用者が気配を確認し、任意で寄り道を開始する。
6. アプリは寄り道スポットへの方角を表示する。
7. 利用者が一定範囲まで近づき、「？」を押してスポットを発見する。
8. 利用者が寄り道を終了し、目的地への案内に戻る。

## 6. 画面と画面遷移

### 6.1 散歩中の表示モード

散歩中画面は、少なくとも次の二つの表示モードを持つ。

- **方角モード**: 目的地コンパスを表示する。寄り道中は、目的地コンパスと寄り道コンパスをスワイプで切り替える。
- **探索マップモード**: 霧、現在地、踏破範囲、寄り道スポットの気配を表示する。

利用者は散歩を終了せずに、二つの表示モードを相互に切り替えられる。切り替えによって目的地、開始時刻、位置情報、選択中の寄り道スポット、発見記録を初期化してはならない。

### 6.2 寄り道コンパス

- 寄り道コンパスは独立した画面ではなく、方角モード内に追加する。
- 利用者が「？」マーカーから寄り道を開始すると、方角モード内に寄り道コンパスを追加する。
- 寄り道中は、目的地コンパスと寄り道コンパスを水平方向のスワイプで相互に切り替えられる。
- 現在どちらのコンパスを表示しているか、名称またはページインジケーターで識別できるようにする。
- 寄り道コンパスを表示中は「寄り道を終了」操作を表示する。
- 「寄り道を終了」を押すと寄り道コンパスを方角モードから除き、目的地コンパスを表示する。
- スワイプはコンパスの表示対象だけを変更し、目的地、寄り道セッション、位置監視を変更しない。

### 6.3 基本遷移

```text
目的地選択画面
      |
      | 目的地を選択して散歩開始
      v
方角モード  <-------------------------->  探索マップモード
  | 目的地コンパス                              |
  |                                            | 「？」から寄り道開始
  |                                            v
  |<-------------------------------------  方角モード
  |                                      ┌─────────────────┐
  |                                      | 目的地コンパス   |
  |                                      |   <スワイプ>     |
  |                                      | 寄り道コンパス   |
  |                                      └─────────────────┘
  |                                            |
  |                                            | 接近後「？」を押す
  |                                            v
  |                                     ランドマーク情報表示
  |                                            |
  +--------------------------------------------+
              「寄り道を終了」後、目的地コンパスを表示
```

ランドマーク情報を閉じた直後の遷移は未決事項とする。ただし、利用者が「寄り道を終了」を実行できる導線を失ってはならない。

## 7. 機能要件

### FR-LD-01 方角モードと探索マップモードの切り替え

- 散歩実行中にのみ切り替え操作を表示する。
- どちらのモードからでも、一操作で他方へ切り替えられる。
- 表示モードは散歩セッションの一時状態として保持する。
- 切り替えによって位置情報の監視を停止または重複開始してはならない。
- 寄り道中に探索マップへ切り替えられるかは未決事項とする。状態モデル上は切り替え可能な設計を妨げないこと。

### FR-LD-02 霧のある探索マップ

- 探索マップは、未踏部分を霧で覆うレイヤーを持つ。
- 有効な位置情報を取得した場合、その位置を踏破情報の更新候補とする。
- 位置精度が許容範囲外の場合、踏破範囲を更新しない。
- 霧レイヤーは地図本体、現在地、軌跡、スポット表示から分離して実装する。
- 霧の濃さ、踏破判定半径、過去の踏破範囲を継承するかは設定可能にする。
- 霧の下で道路、地名、目的地をどこまで表示するかは未決事項とする。

### FR-LD-03 寄り道スポットの気配表示

- 寄り道可能な範囲に未発見スポットが存在する場合、詳細情報を明かさず「？」マーカーとして表示する。
- 発見前の表示から、少なくとも名称と説明文を取得できないようにする。
- 発見前に正確な位置を表示するかは未決事項とする。表示用座標と実座標を別に保持できるデータ構造にする。
- 同時に複数の気配が存在する場合を扱えるデータ構造にする。
- 表示対象を選ぶ規則は、距離だけに固定せず交換可能にする。
- 方角モード利用中の気配通知方法は未決事項とする。

### FR-LD-04 寄り道の開始

- 利用者は探索マップ上の「？」マーカーを選択して寄り道を開始できる。
- 寄り道開始後は方角モードを表示し、目的地コンパスに加えて寄り道コンパスを利用可能にする。
- 一度に進行できる寄り道セッションは一件とする。
- 寄り道開始時に、選択したスポットIDと開始日時を保持する。
- 寄り道開始によって目的地を上書きしてはならない。
- すでに寄り道中に別のスポットを選択した場合の挙動は未決事項とする。初期実装では操作を無効化してよい。

### FR-LD-05 寄り道コンパス

- 寄り道コンパスは方角モード内で目的地コンパスと同じ表示領域を使用する。
- 利用者は水平方向のスワイプで目的地コンパスと寄り道コンパスを切り替えられる。
- 初期表示するコンパスは寄り道コンパスとする。
- コンパスの表示対象を切り替えても、寄り道セッションを終了しない。
- 現在地から選択中の寄り道スポットへの方位角を算出する。
- 端末方位を利用できる場合、端末の向きに追従して矢印を更新する。
- 端末方位を利用できない場合、既存の目的地コンパスと同じ代替表示を使用する。
- 初期実装で表示する案内情報は方角のみとする。
- スポット名、正確な距離、経路、次に曲がる方向は表示しない。
- 将来、距離や接近傾向を追加しても方位計算と画面全体を置き換えずに済む構成にする。

### FR-LD-06 接近判定と「？」ボタン

- 現在地と選択中スポットの実座標から直線距離を算出する。
- 有効な位置情報が所定の発見可能半径内に入った場合、「？」ボタンを有効化する。
- 発見可能半径の数値は一か所の設定として管理する。
- 位置精度が許容範囲外の場合、新たにボタンを有効化しない。
- 一度有効化したボタンを距離変動で再び無効化するかは判定ポリシーとして分離する。
- 接近していない状態では、ボタンを非表示または無効表示にする。どちらを採用するかは未決事項とする。

### FR-LD-07 ランドマークの発見

- 有効化された「？」ボタンを利用者が押すと、対象を発見済みとして記録する。
- 「？」ボタンを押すまで、自動的に発見済みにしてはならない。
- 正誤判定、選択問題、画像認識を要求しない。
- 同じスポットに対する連続操作で発見記録を重複作成しない。
- 押下後にランドマーク情報を表示する。
- 表示する情報の種類と情報量は未決事項とする。
- 情報を取得できない場合でも、発見操作と通常の目的地案内を失敗させない。

### FR-LD-08 寄り道の終了

- 寄り道コンパスに「寄り道を終了」ボタンを表示する。
- 利用者は発見の成否にかかわらず、任意のタイミングで寄り道を終了できる。
- 終了時に選択中の寄り道スポットと寄り道開始日時を進行中状態から除く。
- 目的地、散歩開始日時、歩行中の位置監視、既存の発見記録を保持する。
- 終了時に寄り道コンパスを方角モードから除く。
- 終了後は方角モード内の目的地コンパスを表示する。

### FR-LD-09 発見記録の保存

- 発見済みスポットをアプリ内に保存する。
- 保存単位は利用者が「？」ボタンを押した一回の発見とする。
- 少なくともスポットIDと発見日時を保存する。
- 同一スポットへの再訪を一件に集約するか、訪問履歴として複数保持するかは未決事項とする。
- 散歩ルートおよび発見コレクションを将来共有できるよう、散歩セッションIDとの関連を保持できる構造にする。
- 保存先は既存のデータ保存方針と整合させる。サーバーへ位置情報を送信する変更は、本要件だけでは許可しない。

### FR-LD-10 エラーと継続動作

- 一時的に位置情報を取得できない場合、最後の有効な方角表示を保持する。
- 位置情報を取得できない間、新しい接近判定または発見判定を行わない。
- スポットデータを取得できない場合でも、目的地への通常案内を継続する。
- 地図または霧の描画に失敗した場合でも、目的地コンパスへ切り替えられる。
- 寄り道中に対象スポットを参照できなくなった場合、エラーを表示し、安全に寄り道を終了できる。

### FR-LD-11 東京都オープンデータによるスポット提供

- ランドマークの元データには、東京都または東京都内の自治体が公開するオープンデータを利用する。
- 採用前に、位置座標の有無、対象地域、更新状況、利用規約、ライセンス、クレジット表記、再配布条件を確認する。
- 元データはバックエンド側へ取り込み、アプリ共通の `LandmarkSpot` 形式に正規化する。
- フロントエンドは東京都の配布元や元データ固有の項目名へ直接依存しない。
- 散歩中のリクエストごとに東京都の配布元APIへ中継する方式を前提とせず、取り込み済みデータからランドマークを返す。
- バックエンドは、指定した地理的範囲に含まれる発見前用のスポット情報を返せるようにする。
- 発見後は、スポットIDを指定して詳細情報と出典情報を取得できるようにする。
- 発見前用レスポンスには、名称、説明文その他の発見後情報を含めない。
- データセットを追加または変更しても、フロントエンドのコンパス、接近判定、霧の処理を変更せずに済む共通契約を使用する。
- 元データの取得、変換、検証、反映は再実行可能な取り込み処理として分離する。
- 更新に失敗した場合、直前に正常に取り込めたデータを継続利用できるようにする。

## 8. 状態モデル

画面名だけでアプリ状態を表現せず、散歩、表示モード、寄り道を別々の状態として管理する。

### 8.1 概念状態

```ts
type WalkStatus = "idle" | "active" | "ended";

type GuidanceMode = "compass" | "exploration-map";

type CompassTarget = "destination" | "detour";

interface GuidanceState {
  mode: GuidanceMode;
  activeCompassTarget: CompassTarget;
}

type DetourState =
  | { status: "inactive" }
  | {
      status: "active";
      spotId: string;
      startedAt: number;
      discoveryAvailable: boolean;
    };
```

### 8.2 状態不変条件

- `DetourState.status === "active"` は `WalkStatus === "active"` の場合に限る。
- 寄り道中も `destination` は必ず保持する。
- 選択中の `spotId` は寄り道スポット一覧に存在する。
- `discoveryAvailable` は有効な位置情報による接近判定でのみ `true` になる。
- 発見記録は「？」ボタンの利用者操作によってのみ作成する。
- 表示モードの変更は寄り道状態や散歩状態を変更しない。
- `CompassTarget === "detour"` は `DetourState.status === "active"` の場合に限る。
- コンパス対象のスワイプ切り替えは `GuidanceMode === "compass"` の場合に限る。

### 8.3 イベント

| イベント | 事前条件 | 結果 |
| --- | --- | --- |
| `SWITCH_GUIDANCE_MODE` | 散歩中 | 方角／探索マップを切り替える |
| `START_DETOUR(spotId)` | 散歩中、寄り道なし | 寄り道を開始する |
| `SWITCH_COMPASS_TARGET` | 方角モード、寄り道中 | 目的地／寄り道コンパスを切り替える |
| `LOCATION_UPDATED(position)` | 散歩中、有効な位置 | 方角、霧、接近状態を更新する |
| `DISCOVER_SPOT` | 寄り道中、発見可能 | 発見記録を作成して情報を開く |
| `END_DETOUR` | 寄り道中 | 寄り道を終了し、目的地コンパスを表示する |
| `END_WALK` | 散歩中 | 寄り道を含む散歩中状態を終了する |

## 9. データ要件

以下はAPIの確定契約ではなく、責務を分離するための概念モデルである。外部APIを追加する場合は、実装前に [`api.md`](./api.md) と `shared/contracts/` を同じ変更で更新する。

### 9.1 データ提供構成

```text
東京都オープンデータ配布元
          |
          | 定期または手動の取り込み
          v
バックエンド取り込み処理
  - 取得
  - 形式変換
  - 必須項目と座標の検証
  - 出典・ライセンスの付与
          |
          v
バックエンドのランドマークデータ
          |
          | アプリ共通API
          v
フロントエンド
  - 発見前の気配表示
  - 発見後の詳細表示
```

- 元データ形式を解釈する責務はバックエンドの取り込み処理に置く。
- バックエンドの保存方式は、データ件数、更新頻度、検索方法を確認して実装時に決定する。
- ランドマークAPIは「発見前情報」と「発見後情報」を別の契約として扱う。
- 周辺検索で現在地そのものをバックエンドへ送るか、地図表示範囲や地域IDで検索するかは、プライバシーとデータ量を踏まえて実装前に決定する。
- 採用する検索方式にかかわらず、正確な現在地をアクセスログへ残さない。

### 9.2 寄り道スポット

```ts
interface LandmarkSpot {
  id: string;
  category: string;
  actualLocation: {
    latitude: number;
    longitude: number;
  };
  discoveryContent: LandmarkDiscoveryContent;
  source: LandmarkSource;
}

interface LandmarkDiscoveryContent {
  name: string;
  summary?: string;
  imageUrl?: string;
  attributes?: Record<string, string>;
}

interface LandmarkSource {
  datasetId: string;
  datasetName: string;
  publisher: string;
  sourceUrl: string;
  license: string;
  attribution?: string;
  sourceUpdatedAt?: string;
  importedAt: string;
}
```

`discoveryContent` は発見前の画面へ渡さない。発見前表示用の情報が必要になった場合は、詳細情報とは別の型として追加する。

### 9.3 気配表示

```ts
interface LandmarkHint {
  spotId: string;
  displayLocation?: {
    latitude: number;
    longitude: number;
  };
  categoryHint?: string;
}
```

`displayLocation` は正確な座標を見せない方式に対応できるよう任意項目とする。初期実装で実座標をそのまま流用する場合も、UIが `LandmarkSpot.actualLocation` を直接参照しない構造にする。

### 9.4 発見記録

```ts
interface LandmarkDiscoveryRecord {
  id: string;
  spotId: string;
  walkSessionId: string;
  discoveredAt: number;
}
```

将来の写真、感想、共有状態等は、この記録を破壊せず追加できる任意フィールドまたは関連データとして扱う。

### 9.5 設定値と判定ポリシー

少なくとも次の値をUIコンポーネントへ直書きしない。

```ts
interface LandmarkDiscoveryConfig {
  hintDetectionRadiusMeters: number;
  discoveryRadiusMeters: number;
  maxAcceptedAccuracyMeters: number;
  exploredRadiusMeters: number;
}
```

スポット候補の選定、接近判定、霧の更新は、それぞれ独立した関数またはサービスとして実装する。

## 10. 拡張しやすさに関する要件

### 10.1 責務の分離

実装は少なくとも以下の責務を分離する。

| 責務 | UIから分離する処理 |
| --- | --- |
| スポット供給 | バックエンドAPI、検索、キャッシュ、出典情報 |
| データ取り込み | 東京都オープンデータの取得、正規化、検証、更新 |
| 気配選定 | 現在地から表示候補を選ぶ規則 |
| 方角計算 | 寄り道スポットへの方位角計算 |
| 接近判定 | 「？」ボタンを有効化する規則 |
| 霧・踏破 | 位置ログから踏破範囲を更新する処理 |
| 発見保存 | 発見記録の作成、重複制御、永続化 |
| 表示 | コンパス、マップ、情報表示 |

### 10.2 変更に対する要件

- 寄り道コンパスへ距離を追加するとき、接近判定ロジックを変更せずに済むこと。
- 接近判定半径を変更するとき、画面コンポーネントを変更せずに済むこと。
- スポットのデータ提供元を変更するとき、コンパスとマップを変更せずに済むこと。
- 霧の描画方式を変更するとき、スポット取得と発見記録を変更せずに済むこと。
- 通知方法を追加するとき、気配選定ロジックを再利用できること。
- ランドマーク詳細の項目を追加するとき、発見前に情報が漏れない境界を維持すること。
- 自由散歩モードを追加するとき、目的地を上書きする前提を寄り道機能に持たせないこと。

### 10.3 UI実装上の制約

- コンパスの計算処理を画面コンポーネント内に重複実装しない。
- 目的地コンパスと寄り道コンパスで共通化できる表示部品を利用する。
- 目的地／寄り道の切り替えは、コンパスのデータ対象を切り替える構成とし、画面全体を別画面として重複実装しない。
- 状態遷移はイベント単位で明示し、複数の真偽値の組み合わせだけで表現しない。
- 発見前用データと発見後用データを型または取得境界で分離する。
- 位置更新の購読を画面切り替えのたびに重複作成しない。

## 11. 非機能要件

### 11.1 安全性

- 歩行中の長時間の画面注視を前提としない。
- 操作対象は屋外でも押しやすいタップ領域を確保する。
- アプリは車道横断、立入禁止区域または危険な経路への移動を指示しない。
- 寄り道は任意であり、いつでも終了できる。

### 11.2 プライバシー

- 正確な現在地や歩行履歴をアプリケーションログへ出力しない。
- 初期実装では、位置情報をサーバーへ送信することを前提としない。
- 共有機能を追加する際は、散歩ルートから自宅等を推測できるリスクを別途検討する。

### 11.3 性能と可用性

- 新しい有効な位置情報を取得してから、方角と接近状態を原則1秒以内に更新する。
- 位置更新ごとに全スポットを無制限に走査する設計を避ける。
- 地図またはスポットデータの通信失敗によって散歩セッションを終了しない。
- 位置更新、地図描画、霧描画によるバッテリー消費を実機で検証する。

### 11.4 アクセシビリティ

- 方角、発見可能状態、エラーを色だけで表現しない。
- 「？」マーカーとボタンにはアクセシブルな名称を設定する。
- 寄り道中であることと、元の目的地への案内ではないことを文字でも示す。
- スワイプ操作を利用できない場合に備え、アクセシビリティ操作からもコンパスを切り替えられるようにする。

### 11.5 オープンデータ

- ランドマークデータごとにデータセット名、公開者、配布元URL、ライセンス、必要なクレジットを管理する。
- 発見後の情報表示では、必要な出典表記を確認できるようにする。
- 再配布条件が不明なデータを本番データとして利用しない。

## 12. 受入条件

### AC-LD-01 表示モード切り替え

- [ ] 散歩中、方角画面から探索マップへ切り替えられる。
- [ ] 探索マップから方角画面へ戻れる。
- [ ] 切り替え後も目的地、経過時間、位置監視が維持される。

### AC-LD-02 霧と気配

- [ ] 探索マップの未踏部分に霧が表示される。
- [ ] 有効な位置更新によって踏破情報が更新される。
- [ ] 低精度な位置情報では踏破情報が更新されない。
- [ ] 条件を満たす未発見スポットが「？」として表示される。
- [ ] 発見前にスポット名と説明文が表示されない。

### AC-LD-03 寄り道開始と方角案内

- [ ] 「？」から寄り道を開始できる。
- [ ] 寄り道開始後、方角モード内に目的地コンパスと寄り道コンパスが存在する。
- [ ] 水平方向のスワイプで二つのコンパスを相互に切り替えられる。
- [ ] 表示中のコンパスが目的地用か寄り道用かを識別できる。
- [ ] 寄り道コンパスが対象スポットへの方角を表示する。
- [ ] 初期実装では距離と経路を表示しない。
- [ ] 寄り道開始後も元の目的地が保持される。
- [ ] 同時に二件の寄り道が進行しない。

### AC-LD-04 発見

- [ ] 発見可能範囲外では「？」ボタンを使用できない。
- [ ] 有効な位置情報で発見可能範囲に入ると「？」ボタンを使用できる。
- [ ] 「？」ボタンを押すまで自動的に発見済みにならない。
- [ ] 「？」ボタンを押すと発見記録が一件作成される。
- [ ] 連続して押しても同じ発見記録が重複作成されない。
- [ ] 発見時に正誤判定を要求されない。

### AC-LD-05 寄り道終了

- [ ] 発見前後を問わず「寄り道を終了」を実行できる。
- [ ] 終了すると寄り道コンパスが方角モードから除かれる。
- [ ] 終了後、元の目的地コンパスが表示される。
- [ ] 終了後も散歩セッションと発見済み記録が維持される。

### AC-LD-06 障害時

- [ ] 位置情報が一時的に失われてもアプリが終了しない。
- [ ] 地図の表示に失敗しても目的地コンパスを使用できる。
- [ ] スポット情報の取得に失敗しても目的地への案内を継続できる。
- [ ] 寄り道を継続できない場合、安全に寄り道を終了できる。

### AC-LD-07 オープンデータとバックエンド

- [ ] 採用した東京都オープンデータを、再実行可能な処理でバックエンドへ取り込める。
- [ ] 不正な座標または必須項目が欠けたレコードを検出できる。
- [ ] フロントエンドが元データ固有の形式を知らずに、共通契約でスポットを取得できる。
- [ ] 発見前のAPIレスポンスにスポット名と説明文が含まれない。
- [ ] 発見後のAPIレスポンスからデータセット名、公開者、配布元、ライセンスを確認できる。
- [ ] 元データ配布元に接続できない場合も、直前に正常に取り込んだデータを提供できる。
- [ ] 複数のデータセットを同じ共通形式へ変換できる。

## 13. テスト観点

### 13.1 単体テスト

- 通常目的地と寄り道スポットそれぞれの方位角計算
- 気配表示の候補選定
- 発見可能半径の境界値（内側、境界上、外側）
- 許容位置精度の境界値
- 発見記録の重複防止
- 寄り道状態の開始、発見可能化、終了
- 霧の踏破範囲更新

### 13.2 結合テスト

- 方角画面と探索マップの往復で状態が保持されること
- 「？」選択から寄り道コンパス表示までの遷移
- 模擬位置更新による「？」ボタンの有効化
- 発見記録作成後に通常案内へ復帰できること
- 位置情報またはスポット取得失敗時のフォールバック
- オープンデータ取り込みから共通APIでの取得までのデータフロー
- 発見前APIに詳細情報が混入しないこと
- 元データ更新失敗時に直前の正常データを維持すること

### 13.3 実機テスト

- 方位センサーによる寄り道コンパスの追従
- GPSの揺れによる発見可能状態の不自然な反転
- 霧描画の滑らかさとバッテリー消費
- 屋外での視認性と操作領域
- 通信断中の通常案内と保存済みデータの維持

| ID | 未決事項 | 実装上の暫定方針 |

## 15. 将来要件

以下は初期実装の受入条件に含めない。

### 15.1 寄り道案内の拡張

- 寄り道コンパスへの距離表示
- 近づいている／遠ざかっている状態の表示
- 複数スポット間の切り替え
- 気配出現時の振動、音または画面通知

### 15.2 自由散歩モード

- 目的地を設定せず散歩を開始する。
- 周辺スポットを通過した場合に気配を通知する。
- 目的地なしでも探索マップ、発見、保存を利用できる。

### 15.3 コレクションと共有

- 発見した場所をコレクションとして一覧表示する。
- 散歩全体のルートと発見場所を一つの記録として表示する。
- 家族や友人へ散歩ルートと発見コレクションを共有する。
- 共有前に開始地点、終了地点等の機微な位置情報を隠せるようにする。

### 15.4 振り返り

- 散歩終了後に歩行ルート、踏破マップ、発見場所を振り返る。
- 写真、感想、気づきを発見記録に追加する。

### 15.5 教育利用

- 学校教育を対象とするかを改めて検討する。
- 対象とする場合は、教員による設定、グループ利用、安全管理、成果物等を別要件として定義する。

## 16. 実装開始前に必要な決定

次の事項は、初期実装を動作させるため最低限の暫定値またはデータが必要である。

1. 初期実装で利用する東京都オープンデータのランドマークデータセット
2. 気配の検出半径
3. 「？」ボタンを有効化する発見可能半径
4. 接近判定に利用できる位置精度の上限
5. 踏破範囲を更新する半径
6. 発見後に最低限表示する仮の情報項目
7. 発見記録の端末内保存方式
8. 正規化後のランドマークデータを保持するバックエンドの保存方式
9. 周辺スポットAPIの検索条件と、現在地をバックエンドへ送信するかどうか
10. 元データの更新確認および再取り込みの頻度

これらを暫定決定する場合は、値、決定日、変更理由を追跡できるようにする。
